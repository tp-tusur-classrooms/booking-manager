# Работа над проектом

## Ветки и путь задачи

- `main` — проверенный результат для выпуска, основная ветка репозитория.
- `develop` — интеграция задач текущей разработки.
- `feature/<task-id>-<name>` — новая возможность, например `feature/DEV-01-repository-ci`.
- `fix/<task-id>-<name>` — исправление, например `fix/DEV-02-login-validation`.

`task-id` содержит буквенный код и номер (`DEV-01`), `name` — короткое имя
латиницей в нижнем регистре с дефисами. Старые `master` и `dev` сохранены
для истории; новые задачи основываются на `develop`.

1. Обновите `develop` и создайте рабочую ветку:

   ```sh
   git fetch origin
   git switch develop
   git pull --ff-only origin develop
   git switch -c feature/DEV-01-repository-ci
   ```

2. Внесите изменения, запустите проверки из README и опубликуйте свою ветку.
3. Создайте PR в `develop`, заполните шаблон с issue и способом проверки.
4. Получите минимум одно одобрение другого участника, устраните замечания
   и дождитесь всех обязательных проверок. После новых коммитов ревью повторяется.
5. Слейте задачу в `develop`. Для выпуска создайте отдельный PR `develop` → `main`
   с перечнем задач; для него также нужны проверки и ревью. Используйте merge commit
   при переносе `develop` в `main`, чтобы сохранить общую историю веток.

Прямой push, force push и удаление `main`/`develop` запрещены, в том числе
администраторам. Для слияния ветка должна быть актуальна относительно целевой,
обсуждения должны быть разрешены. При конфликте или отставании обновите свою
ветку от целевой и повторите проверки. Нельзя обходить ревью или подменять статусы.

## Обязательные проверки CI

Workflow `.github/workflows/ci.yml` запускается на каждом PR в `main` и `develop`,
на обновлении PR (включая смену целевой ветки) и после слияния в эти ветки.
Фильтров по путям нет: обязательная проверка не останется в ожидании из-за
изменения только документации. Любой ненулевой код завершения блокирует слияние.

| Проверка | Что проверяет |
| --- | --- |
| `PR policy` | Рабочие ветки направлены в `develop`; в `main` принимается только собственная `develop` |
| `Backend` | Python 3.13, `uv sync --locked --dev`, Ruff lint и форматирование всего проекта, все тесты unittest из `tests/` |
| `Frontend` | При наличии `frontend/`: Node.js 24, `npm ci`, `npm run lint`, TypeScript `npm run typecheck`, `npm run build` |

Обязательность этих трёх статусов и одного одобрения задаётся в настройках
защиты **обеих** веток GitHub, вместе с запретом обхода администраторами,
force push и удаления. При изменении имён job необходимо одновременно обновить
список required status checks в защите веток.

Используется существующая конфигурация Ruff в `pyproject.toml`; её ослабление
ради прохождения CI недопустимо. Новые тесты добавляйте в `tests/test_*.py`.
Зависимости фиксируются в `uv.lock`; изменение зависимостей сопровождается
обновлением lock-файла. CI не обновляет его автоматически.

## Подключение фронтенда

Фронтенда сейчас нет, поэтому `Frontend` явно сообщает об этом в отчёте CI.
При его добавлении используйте каталог `frontend/`, включите `package.json`
и `package-lock.json` в один PR. Обязательны scripts `lint` и `build`,
а для TypeScript также `typecheck` (например, `tsc --noEmit`).
Наличие TypeScript определяется по зависимости `typescript`, конфигурации
`tsconfig*.json` или исходникам `.ts`/`.tsx`/`.mts`/`.cts`.
Пустой каталог, отсутствие lock-файла или обязательного script приводят к ошибке CI.
Фронтенд начнёт проверяться автоматически в том же PR, в котором он добавлен.
Команды должны завершаться с ошибкой при нарушении правил; `--if-present`
и подавление ошибок для обязательных проверок не используются.

## Права и секреты

- Workflow имеет только `contents: read`; checkout не сохраняет токен в Git.
- Используется `pull_request`, без выполнения кода PR через `pull_request_target`.
- Actions закреплены полными SHA, версия uv фиксирована. Рабочие секреты CI не нужны.
- `config/prod/`, `.env*` (кроме `.env.example`) и локальные артефакты исключены из Git.
- В `config/example/` и Compose находятся только демонстрационные данные для
  локальной разработки. Не используйте их в рабочем окружении.
- Реальные пароли и ключи храните в защищённых настройках окружения или GitHub
  Actions Secrets. Не добавляйте их в workflow, исходники, PR или журналы CI.
- В Settings → Actions → General задайте для `GITHUB_TOKEN` read-only permissions
  и отключите возможность одобрять PR через Actions.
